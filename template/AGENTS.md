# AGENTS.md — 本项目的工程铁律

本文件是**人类与所有 AI agent 的单一事实源**。每条规则 1–3 行，需要展开的细节链接到对应文件（一个事实只在一处展开）。项目专属约定（语言、目录、命令、命名）补在文末「项目约定」。

> **若搭配 Superpowers 使用**：开发管线（brainstorming → spec → writing-plans → TDD 执行 → 评审 → 验证 → 收尾）由 Superpowers 驱动，冲突时**以 Superpowers 为准**。本文件只提供它不管的：质量铁律、项目级记忆（`docs/spec.md` + ADR）、硬门禁、AI 权限、技术清单。特性级设计文档在 `docs/superpowers/specs/`，项目级活需求在 `docs/spec.md`，两者分工不合并。分工与技能取舍见 `docs/with-superpowers.md`。

## 核心元纪律（治 vibecoding 的典型毛病）

1. **改之前先读规则**：动手前先读本文与被改区域的局部规则；评审代码时先打开「该改动必须满足的规则」，再看 diff——凭记忆判 diff 正是漏网的原因。
2. **新行为先找扩展点**：优先挂在已有扩展点/边界上；要改主循环、核心模块或加 `if` 分支前，先说明为何无法扩展实现。
3. **通过的检查不重复全量跑**：按「变更面 → 最小证据」选择验证（见技能 `definition-of-done`）；全量回归交给 CI。报告只写**实际跑过**的命令与结果，不许声称跑过没跑的测试。
4. **人读懂 AI 的 diff 才合并**：AI 写的每一行，人类负责评审并理解；不能理解就不能合入。AI 参与度高的实现必须走更严的评审（见 `docs/ai-usage.md`）。
5. **改行为必须改它的测试与文档**：测试描述的是「当前行为」而非「永远正确」；行为变化时同步改测试和受影响文档，并在变更说明里解释为何旧行为过时。

## 反合理化（识别并打断"找借口"）

出现以下念头时视为红旗，回到规则而非绕开：

- "就这一次跳过测试/评审" → 那是合理化，停。
- "先做了再说，之后再补测试/文档" → 先补上该有的验证与文档。
- "这改动太小，不用守规则" → 小改动同样受铁律与硬门禁约束。
- "我记得规则，不用重读" → 规则会演进，开工/评审先读当前版本。
- "测试红了，改断言或 normalizer 让它过" → 修代码或修夹具，不在比对器里放水。
- "AI 说做完了就是做完了" → 只信实际跑过的检查与机器判定，不信自述。

## 边界与类型

6. **只在信任边界做运行时校验**：在「解析/配置输入、网络线、模型或工具返回的 JSON、持久化数据、子进程/worker」处校验；类型系统已保证的同进程内部，不加多余运行时检查。
7. **共享状态必须有唯一 owner**：不新增模块级/全局 `current`、`active`、`selection` 单例或隐藏全局缓存；状态挂在明确的服务或实例上。
8. **一个值只表达一个事实**：缺失 / 未知 / 空用可区分的方式表达，不混用 `null`/`undefined`/`""` 互相掩盖（语言支持时优先可辨识联合/判别标签）。

## 依赖与复杂度

9. **先找现成方案**：能由维护良好的依赖真正删掉自持代码与测试时优先复用；为单一用途新建抽象层/服务/工具函数前，先证明现有方案不够。
10. **默认值必须有依据**：新增的可配置项、默认行为、公开 API，都要能指出当前消费者或用例证据；拿不准就要求显式传入，而不是给一个没人验证过的默认值。

## 文档与决策

11. **开工先读 `docs/spec.md`，以它为当前需求的事实源**：它只写「当前有效」需求（现在时），需求变了先更新它再动手。「开放问题」里未定的点不要擅自决定，先问人。需求发生方向性变化时，更新 spec 并在 `docs/adr/` 记一条演进（从 A 到 B、放弃了 A 的什么），正文不留已作废的旧方向。
12. **有持久取舍才写决策记录**：架构/格式/兼容性等不可逆决策写入 `docs/adr/`（模板见该目录）；机械性局部改动免写。决策被推翻时新开一篇互链，不回改旧结论。
13. **踩非显然坑写复盘**：机制不明显、且是测试/工具/约定漏洞放走的 bug，写进 `docs/postmortem/`，重点回答「为什么每道安全网都放它过去、加了什么让同类问题下次必炸」。
14. **文档随代码同 PR 更新**：行为、配置、公开契约变化时，同一次改动更新受影响 README/注释；注释讲清「契约与为什么这么设计」，不复述代码、不写推理流水账。

## 变更说明

15. **按模板提交变更说明**：`.github/PULL_REQUEST_TEMPLATE.md`（个人项目也建议逐任务收尾填写）：动机 / 改动（接口与行为分开）/ 测试（只列跑过的）/ AI 参与度。

## 质量门禁（渐进启用，见 README）

- 已启用的门禁在本文件「项目约定」登记；每条能被机械判定的约定，最终都应升级成「会失败、且有反例证明它真会红」的脚本或 CI，而不是只靠本文靠人记。
- 新增门禁先 `report`（只告警）稳定后转 `block`（阻断）；不为通过而弱化断言、吞错、加超时/重试。
- **AI 自主边界**：AI 可自主扫描信号、并以 `report`（只告警、可逆）模式新增观察性门禁；但把门禁转为 `block`、提高阈值、引入高维护成本设施（AST 依赖检查、CI DAG 等）、或删除/放宽已有门禁，**必须先经人确认**并给出触发证据（哪几次评审/事故/度量，见 `docs/scaling.md`）。

## 会话接续（新 agent 如何重建状态）

- 新会话/新 agent **不继承上一会话记忆**，靠仓库里的事实源重建：先读 `AGENTS.md`、`docs/spec.md`，再看 `docs/superpowers/plans/` 最新 plan 的任务勾选与 `git log` 近期进展，按需深入而非全量读项目。
- 动手前先用 3–5 句话向人**回放**你理解的「当前目标 / 已完成 / 下一步 / 发现的不一致」，经确认再继续——主动暴露记忆偏差，不要假设自己对了。
- 状态**当下落盘**：需求变化更新 `spec.md`、任务完成勾选 plan、进度频繁 commit；知道将开新会话时，让当前 agent 把「做到哪/下一步/未决」写进 plan 或 docs 作为交接。

## AI 的 git 与合并权限

- **AI 可自主**：commit、建分支、跑测试、修 lint、读 git 历史、在独立 worktree 里工作。
- **必须先经人确认**：push 到共享分支、merge、force push（即便用 `--force-with-lease`）、删分支、发布、改 CI/门禁配置。
- **"是否通过检查"由脚本与 CI 判定，不由 AI 自己宣布**：AI 可以触发检查、修复问题，但不能自己宣告"通过了"；报告只写实际跑过的命令与结果。
- 原则：AI 负责**触发与修复**，机器负责**判定与拦截**——不让 AI 既当选手又当裁判。
