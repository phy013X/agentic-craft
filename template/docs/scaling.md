# 何时补充重型机制（升级触发条件）

模板默认很轻。重型机制**按反复出现的痛点触发，不按日历或规模数字机械触发**。判断标准：

- 同一类问题被人工评审**反复抓到 ≥3 次** → 值得写成门禁。
- 一个 bug **逃逸**到用户或合并后 → 先写复盘，再决定加什么护栏。
- 只是"感觉应该更规范"、还没有真实痛感 → **先不做**。提前引入重型机制是小项目被流程压死的主因。

## 各机制的触发信号与最小落地

### 1. 棘轮技术债门禁（已在可选层，建议第一天就有）
- **触发**：任何项目。这是唯一"越早越好"的门禁。
- 见 `optional/node/README.md`。

### 2. 生成物漂移检查
- **触发**：仓库里出现任何"由工具生成、不应手改"的文件（lockfile、Prisma/OpenAPI/protobuf 产物、生成的类型或目录清单）。
- **最小版**：CI 加一行 `pnpm install --frozen-lockfile` 或 `生成 && git diff --exit-code`。
- 成本极低，一旦有生成物就该加。

### 3. per-file 覆盖率门禁
- **触发**：全局覆盖率已不低（≳70%），但评审仍反复发现"这个核心函数没测"；或出现过"核心路径没测导致线上 bug"。
- **前置**：已有像样的测试习惯。**测试还不到几十条时先别上覆盖门禁，先写测试**——否则会逼出凑数的空断言。
- **最小版**：覆盖率工具开 `perFile`，阈值从较低值起步、逐季收紧；豁免必须逐文件列名写理由。
- **心智**：未覆盖行优先当"死代码"处理，而非急着补测试凑数。

### 4. 依赖边界 / 方向检查
- **触发**：模块/包 ≥8 个，且评审反复抓到"这个 import 方向不对"，或出现过循环依赖、下层反向依赖上层。
- **前置**：你已经有清晰的分层/分域约定（否则没有"方向"可卡）。
- **最小版**：优先用现成工具——`dependency-cruiser`、`eslint-plugin-import` 的 `no-restricted-paths`、或一个几十行正则脚本扫 import 方向。
- **完整版**（仅 monorepo）：像 dsh 那样用 AST 从源码反推依赖声明、未归类的跨包边即违规。**不要在只有三四个模块时自建 AST 检查器。**

### 5. capability seam（接口/实现/消费 三角色）
- **触发**：同一能力出现 **≥2 个实现**（本地/远程、mock/真实、多供应商），或需要让第三方/插件扩展。
- **反模式**：只有一个实现时就拆三层 = 过度设计。先单实现，等第二个实现出现再抽接口。
- **最小版**：一个 interface + 一个注册点；上层只依赖接口。

### 6. CI 分层 / 并行 / 分阶段触发
- **触发**：单次 CI >10 分钟、或 CI 账单/等待成为明显瓶颈。
- **最小版**：lint / test / build 拆成并行 job；按变更路径过滤无关 job；重测试放夜间或合并后。
- **完整版**：差量检查、merge-base 预检、审批后才跑贵 job、`off/report/block` 灰度。

### 7. CODEOWNERS / owner 审批
- **触发**：团队 ≥5 人，或出现"有人 approve 了但其实不懂这块代码"导致的事故。
- **最小版**：CODEOWNERS 按目录指定 owner，要求 owner 审批而非任意人点赞。
- **个人/小团队**：退化为一条纪律——AI 写的代码，人读懂 diff 才合并。不要上加权 blame 那套（需多评审者+词法分析，过重）。

### 8. stacked PR 工具链
- **触发**：频繁出现"PR B 依赖 PR A"，且手工改 base（retarget）反复出错或漏改。
- 见 `docs/parallel-development.md` 形态 3。

## 升级决策速查

| 观察到的信号 | 动作 |
|---|---|
| 同类评审意见出现 ≥3 次 | 写成 lint 规则或 gate |
| bug 逃逸到用户/合并后 | 写 postmortem + 加对应护栏 |
| 出现代码生成物 | 加生成物漂移检查 |
| 核心路径没测导致 bug | 上 per-file 覆盖门禁 |
| 模块 >8 且依赖方向乱 | 上依赖边界检查 |
| 同一能力 ≥2 实现 | 抽 capability seam |
| CI >10 min | CI 分层/并行 |
| 团队 >5 人 | CODEOWNERS owner 审批 |

## 能否交给 agent 自主判断？（分工边界）

**不能全自动，但可以分工。** 添加重型机制是一个"成本立即、收益延迟、且影响所有后续开发"的决策。agent 适合提供信号与可逆实现，人必须握住"强制化"的决定权。

### 为什么不能全交给 agent
1. **加东西的系统性偏差**：LLM 倾向用"做更多"来展示价值，让它判断"要不要加机制"会天然偏向加。dsh 里大量规则（"每个抽象要有当前 owner 与需求"、"默认值要有消费者证据"、"只服务单一调用者的 public 方法视为 API 膨胀"）正是在对抗这种倾向——对人如此，对 AI 更如此。
2. **痛点是跨时间信号**：触发条件是"同类问题被反复抓 ≥3 次""bug 曾逃逸"，这些活在历史里。单次会话的 agent 只看到当前快照，看不到评审与事故历史，无法真正判断"是否反复出现"。
3. **长期与组织成本 agent 评估不了**：门禁的维护负担、对开发节奏的摩擦、以及"团队开始无视红灯"的文化腐蚀，是长期社会性成本，一次会话算不清。
4. **"值不值"取决于项目阶段**：快速试错期 vs 要维护十年的框架，同样的痛点结论相反。这是产品/人的权衡，不是技术信号能推出的。

### 分界标准：可逆性 + 影响半径
| 动作 | 谁决定 |
|---|---|
| 扫描现状、报告信号（文件/包数、CI 时长、重复出现的评审意见） | agent 自主 |
| 以 **report（只告警、不阻断）** 模式新增观察性门禁 | agent 可自主（可逆、低摩擦） |
| 给出最小实现 + 触发证据 | agent 自主 |
| 把门禁转为 **block**、提高阈值 | **必须人批准** |
| 引入高维护成本设施（AST 检查器、CI DAG、加权审批） | **必须人批准** |
| 删除 / 放宽已有门禁 | **必须人批准** |

一句话：**"加观察性的、可逆的"可以 agent 自主；"加强制性的、有长期维护成本的"必须人拍板。**

### 把"判断"转成"举证"
agent 提议加强制门禁时，必须在 PR/ADR 里给出**触发信号证据**（哪几次评审、哪次事故、哪个度量），人据此拍板。这样"agent 能否判断"就转化为"agent 能否提供足够证据让人判断"——后者它能做好，也正好复用本模板的 ADR 机制。

## 反模式（比"不升级"更糟）

- **提前优化**：没痛点就上重型机制，小项目被流程拖死。
- **一刀切门禁**：新门禁直接 `block` 砸断所有人 → 大家想办法绕过。先 `report` 再 `block`。
- **为门禁而门禁**：门禁必须有"故意造错能红"的负对照，否则可能在静默失效。
- **只加不维护**：门禁和规则要随项目演化增删；过时的门禁比没有更糟（教人无视红灯）。
