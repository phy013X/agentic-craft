# 找简化点

目标是**删掉被维护的义务**（API、表示、生命周期状态、配置路径、依赖、测试、文档）。宁要几个有充分证据的候选，不要一堆删除数。区分"做一次调查"与"获得实施授权"。

## 发现角度（用问题引导）

- **这个特性有完整的生效路径吗？** 追踪生产者→转换→消费者→可观察结果。一个被到处复制的字段可能根本没有 setter、没有 reader，或所有实现都拒绝它。配置/CLI 透传要追"权威读取与优先级"，找出被遮蔽的转发值。
- **这个区分会改变消费者的行为吗？** 不改变任何消费者决策的字段/分支/适配器，优先删。区分"删除这个区分"与"挪动它的声明"。
- **能不能用更小的显式行为取代整个子系统？** 固定间隔、调用方传入、上报激活失败，可能替代通用日历/持久默认值/自动回滚。要说清"放弃了什么能力、删掉了哪些机制"。
- **消费者能不能直接读权威值？** 复制历史、提升账本、缓存旁的失效事件——若能按需推导/复用，可连带删掉订阅、保留数据、过期处理、恢复路径。
- **是不是把"组合"误当成了"策略"？** 可选服务的存在性、provider 方法可以表达"可用性"，而不必决定部署行为；显式配置或调用方意图操作可能删掉注册表和依赖检查。

## 证明可达性与取舍

- 搜索精确符号、属性读写、判别字段、事件/wire 字符串、配置 key、包名，以及 `.method(` 与 `method(` 两种形式。**测试与类型声明能展示契约，但不能证明有真实的生产者/消费者。**
- 注意动态加载：manifest 驱动的挂载、生成物、公开第三方扩展点，即使仓库内零调用也可能是**有意为之的公开 API**。
- 每个候选记录：当前 owner、生效的生产/消费路径、删了什么、留了什么、能力/兼容性影响、**最强的保留理由**。
- **拒绝**：破坏了仍需保留的义务、只是把同样复杂度挪了位置、或没有实质减少的候选。

## 保留所有权与失败语义

- 对拷贝/冻结/校验/回调捕获，说清值的来源、下一个 owner、信任边界。同进程类型化调用通常借用只读值；parser/config/队列/模型 JSON/持久化/worker/进程/wire 边界拥有或校验其输入。
- 对异步机制，把每个 promise、标志位、取消路径、disposer 映射到 owner 与状态转换。**只有表达同一事实的机制才能合并**；保留同步发布、回滚、回调收敛、dispose-to-quiescence。

## 替换基础设施要"净减少"

- 优先复用现有依赖与语言内置能力，再考虑新增包。说清替换**删掉了哪些实现与专属测试**、引入的维护与传递成本、残余胶水必须保留的行为。
- 一个"覆盖了框架、但为了加限制还得重建同样框架"的库不是简化。

## 记录与验证

- 实质性提案走 ADR（Problem/Decision/Alternatives/Consequences），含消费者证据、删掉的维护成本、放弃的能力、可观察验收。局部小改进写成 `TODO/FIXME` 即可，不必单独立档。
- 报告：调查了哪些区域、支撑的候选、有意义的否决/暂缓、实际跑过的命令。**没验证过的搜索不要声称"穷尽"。**
