# 代码评审

## 前置（不可跳过）

1. 核实真实的 base 与改动范围：改了哪些文件、哪些模块被牵连（含未直接改动但受影响的调用方）。
2. **先打开本改动必须满足的规则**（根 AGENTS.md + 被改区域的局部约定 + 相关 ADR），**再读 diff**。凭记忆判 diff 是漏网的主因。
3. 区分「机器已强制的」（lint/类型/已有门禁为绿即可，不重复报）与「只有人能判的语义问题」。本技能只管后者。

## 逐条语义检查

- **接口两侧**：每个改动的函数/类型/事件/配置，追到**调用方与被调用方两侧**，确认契约两端都更新、没有漏改的一侧。
- **错误路径**：失败时状态是否仍一致？错误是否被 `catch` 后静默继续？用户/调用方能否看到可行动的错误信息？拒绝「catch-and-continue」吞错。
- **并发与生命周期**：是否存在 await 期间的取消/竞态？回调是否收敛、清理是否「到静止」（等待退出/关闭，而非仅 kill）？新注册的资源是否有释放路径？
- **范围 / 所有权 / 必要性**：PR 自带的需求、检查、说明是**待评估的设计选择**，不是它必要性的证据。每个新公开方法/默认值/抽象，都要问「当前消费者是谁、证据在哪」；只服务单一内部调用者的新公开 API 视为膨胀。
- **共享状态**：是否引入了新的全局/模块级单例？状态 owner 是否唯一？
- **边界完整性**：限制（长度/大小/超时）是否施加在**含包装与元数据的最终结果**上，而非中间值？
- **测试有效性**：测试是否走真实入口（真实装配/真实命令）？断言能否在目标回归上**真的失败**？每个新验收规则要有一个「故意造错」的反例证明它会红。
- **（AI 项目）模型视角**：站在模型角度检查它实际收到的 prompt、工具 schema、返回结果，而不是只看人类视角的代码。

## 输出规范

- 缺陷 + 位置（file:line）+ 影响 + 证据；**阻塞项（blocker）与建议分开**列。
- 一个坐实的 blocker 胜过一堆 nitpick。不为凑数报告风格琐事。
- 明确写出「本次未覆盖/无法判断的部分」，不假装已审全部。
